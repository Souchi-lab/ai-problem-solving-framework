# Case: SoChi BLOCKS

## このケースの位置づけ

SoChi BLOCKS は、AI Problem Solving Framework v0.1 の**最初の検証ケース**である。

このケースを通じて、フレームワークの以下の点を検証する：

1. **Goal → Plan → Build → Review → Improve** のループが実際に機能するか
2. Planner / Builder / Critic の役割分離が有効に働くか
3. 異なるドメイン（UX・エンジニアリング・コンテンツ）の問題を同じループで扱えるか
4. `runs/` に蓄積したログが次の run に活かせるか

---

## なぜ SoChi BLOCKS が適しているか

SoChi BLOCKS は**ミニスタートアップ構造**を持つ実験環境として、以下の理由で理想的である。

### 1. マルチドメインの問題が同時に存在する

- **Engineering**: Webアプリのパフォーマンス・機能改善
- **Design**: UX・UI・ユーザーフロー改善
- **Algorithm**: パズル生成・難易度設計
- **Content**: ゲーム説明・教材・SNSコンテンツ
- **Marketing**: SNS導線・ランディングページ・CTA最適化

一つのプロダクトで「ドメイン横断の一般化」を検証できる。

### 2. フィードバックループが速い

小規模プロジェクトであるため、
変更の効果確認が速く、ループを短期間で複数回回せる。

### 3. 課題の積み上がりがある

既存の課題（直帰率・UX・パズル品質など）が具体的に存在し、
「架空の問題」ではなく**実際の問題**でフレームワークをテストできる。

### 4. 失敗しても影響範囲が小さい

フレームワーク自体の試行錯誤による影響が限定的で、
実験的な運用がしやすい。

---

## 検証する観点

| 観点 | 内容 |
|---|---|
| Domain independence | Engineering / UX / Content など複数ドメインを同じ構造で扱えるか |
| Agent replaceability | Planner / Builder を別の AI に差し替えても結果に一貫性があるか |
| Reproducibility | 過去の run のログを参照して、改善の経緯を追跡できるか |

---

## transcript.md の価値

SoChi BLOCKS のような実験ケースでは、run ごとに `transcript.md` を生成することを強く推奨する。

### 実験記録として

各 run で「何を試し、どう判断し、何が一般化されたか」の流れを残せる。
後から「あの run ではなぜその判断をしたか」を追跡できる。

### 学習資産として

Planner の問題構造化・Builder の判断・Critic の評価観点などのパターンが
複数 run にわたって蓄積される。
フレームワーク自体の改善に使える。

### 他人への共有資料として

「SoChi BLOCKS でこのフレームワークをどう使ったか」を
複数ファイルを開かせずに一枚で伝えられる。
チームへの説明・レビュー依頼に活用できる。
