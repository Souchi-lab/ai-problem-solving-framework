# SoChi BLOCKS — Goals

## 想定される課題

### UX 改善
- [ ] トップページの直帰率が高い → ゲームの価値が伝わる前に離脱している
- [ ] ゲームの遊び方が分かりにくい → 初回ユーザーの離脱
- [ ] モバイル操作性の課題 → スマホでの体験が PC に比べて劣る
- [ ] ゲームクリア後の次アクションが不明確 → リテンション機会の損失

### Web アプリ改善
- [ ] ページロード速度の改善 → 初期表示が遅い
- [ ] パズル選択フローの改善 → レベルに合ったパズルを見つけにくい
- [ ] プログレス保存 → 進捗が次回訪問に引き継がれない
- [ ] アクセシビリティ対応 → キーボード操作・スクリーンリーダー対応

### パズル生成
- [ ] 難易度の均一化 → 同じ「難易度★3」でも体感が大きく異なる
- [ ] パズルパターンの多様化 → 似たパターンが多く飽きやすい
- [ ] 解法ユニーク性の保証 → 複数解があるパズルのユーザー体験への影響
- [ ] 新規パズル量産フロー → AI を使ったパズル生成・品質チェックの自動化

### SNS 導線改善
- [ ] SNS → サイト の導線が弱い → フォロワーがサイト訪問に繋がっていない
- [ ] シェア機能の整備 → クリアしたパズルをシェアする導線がない
- [ ] SNS 投稿の一貫性 → トーン・内容・頻度が安定していない
- [ ] バイラル要素の設計 → ユーザーが自然にシェアしたくなる仕掛け

### 教材化
- [ ] パズルを教育コンテンツとして再構成する → 学校・塾向けの教材パッケージ
- [ ] 難易度別カリキュラムの設計
- [ ] 保護者・教育者向けの説明コンテンツ
- [ ] 学習効果の可視化（どんな力が育つか）

## 推薦: 最初に着手する run

> **候補 A — SNS 投稿テンプレート作成**
> `runs/2026-03-15_sochi-blocks_sns-post-template/`

### 理由

**1. ループ速度が最速**
Goal → Plan → Build → Review → result.md まで、数時間〜半日で 1 周できる。
フレームワーク自体の動作確認・改善サイクルを最短で回せる。

**2. コード不要で framework を検証できる**
Engineering の準備なしでループを回せるため、
フレームワークの仕組み（handoff / model-assignment / ループ記録）の検証に集中できる。

**3. Generalization しやすい**
「SNS投稿 × AI生成」のパターンは、業務DX・教材コンテンツ・他プロジェクトへの
横展開が最もしやすい。result.md の Generalization セクションに知見を残しやすい。

**4. 失敗コストが低い**
成果物がテキストのみなので、悪ければ捨てて再生成できる。
フレームワークの実験として理想的なリスクプロファイル。

**5. マルチモデル運用を体験しやすい**
JuniorBuilder（Gemini Flash）でバリエーション生成 → Builder（Claude）で統合・仕上げ → Critic（GPT-4o）でレビュー
という multi-model pipeline を実際に試せる最初の機会になる。
