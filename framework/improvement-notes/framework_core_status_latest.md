# APSF Framework Core ステータス・リスト 🛠️

UI 以外の「フレームワークの設計・ロジック」に関する進捗と最新の課題リストです。

---

## ✅ 達成済み (Core Milestones)

*   **[P0] ディレクトリ・トポロジーの統一**:
    *   子ランが親ランのディレクトリ直下にあっても、並列にあっても再帰的に検出・管理できるロジックを確立。命名規則への過度な依存を解消。
*   **[P1] フェーズ判定のロバスト化 (Phase Detection)**:
    *   `execution-assignment.md` がない過去の run や、手動で作成された不完全な成果物に対しても、フォールバックして正しくフェーズを推定できるロジックを実装。
*   **[P2] 意思決定プロセスの永続化 (DB Sync)**:
    *   `viewer.db` により、アクションの実行履歴（exit code やエラー内容）とリワーク時のフィードバックコメントが永続化され、リロード後も文脈が失われない仕組みが完成。
*   **[P2] 運用優先順位の外部管理**:
    *   `priority-index.yaml` の導入により、エージェントやオペレーターが「今どの Run に注力すべきか」をフレームワーク外から制御可能に。

## ⚠️ 進行中 / 次のステップ (Ongoing Logic)

### 1. 「リワーク数」の定量的把握 (Rework Metrics)
- **現状**: ユーザーさんにより `ReworkBadge` が UI に追加。
- **次の課題**: `review_*.md` の回数や DB への保存回数をカウントし、一つの Run が「何回の試行錯誤を経て完了したか」を定量的に可視化するロジックのバックエンド実装。

### 2. 実行環境と文書の乖離 (CLI vs Doc Drift)
- **現状**: Viewer の UI は高度化しているが、`apsf next` や `apsf-claude-act.ps1` 側の判定基準との細かい差異が残る可能性がある。
- **改善案**: Phase 判定のロジックを共通モジュール（`apsf.orchestration.phase_detector`）へさらに集約し、CLI と Viewer で 100% 同一の判定結果を保証する。

### 3. Role 責務と Human Stop の厳格化
- **現状**: Critic Role が `human` に設定されていても、自動実行スクリプトがそのまま突き抜けてしまう問題（メモ指摘事項）。
- **改善案**: `execution-assignment.md` の Role 設定を `api.py` 側でも読み込み、特定の Role が `human` の場合は実行をロックする安全ガードの実装。

## 💎 近未来のコア拡張 (Future Core)

*   **「過去の失敗」の自動参照 (RAG-ready DB)**:
    *   `viewer.db` に蓄積された過去の失敗ログや Rework コメントを、新しい Run の `PLAN_NEEDED` フェーズで Planner エージェントへ提供し、「同じ轍を一発で回避する」仕組みへの発展。
*   **「フェーズ遷移の自動評価」**:
    *   成果物の内容量だけでなく、モデル（Codex 等）が非同期で「その成果物が次のフェーズに進むに値するか」を事前チェックする機構の導入。
