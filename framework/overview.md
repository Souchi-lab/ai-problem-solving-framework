# Framework Overview

## このフレームワークが解きたい問題

AIを使った問題解決は、現状「場当たり的なプロンプト」になりがちだ。

- 問題の定義が曖昧なまま AI に投げる
- Plan なしに Build から始める
- Review を省略して完成とみなす
- 同じ失敗を別の問題でも繰り返す

このフレームワークは、その構造的な欠陥を補正する。
AIの出力能力を最大化するために、**人間とAIの役割分担と手順を明文化する**。

---

## 一般化の狙い

このフレームワークが狙う一般化は 3 層ある。

### 1. ドメイン横断（Domain independence）

「SoChi BLOCKS のパズル改善」も「業務DXの申請フロー改善」も、
同じ問題解決ループで扱えるようにする。

ドメイン固有の知識は `cases/` に分離し、`framework/` はドメイン非依存に保つ。

### 2. Agent 交換可能性（Agent replaceability）

Planner に Claude を使おうと ChatGPT を使おうと、
`framework/agents/planner.md` に定義された責務と入出力形式は変わらない。

特定の AI モデルへの依存を `agents/` 定義に閉じ込め、
フレームワーク全体は中立設計を維持する。

### 3. 再現性（Reproducibility）

`runs/` に実行ログを残すことで、
同じ問題に別の日・別の人・別のAIで再挑戦した際の比較ができる。

何が成功で何が失敗だったかを記録し、次に活かせる構造にする。

---

## 基本思想：問題解決の完全ループ

このフレームワークが目指す完全ループは以下の通り。

```
Problem       ← 問題の発見・定義
  ↓
Structure     ← 問題の分解・構造化
  ↓
Generate      ← 解決オプションの生成
  ↓
Evaluate      ← オプションの評価
  ↓
Select        ← アプローチの選択
  ↓
Execute       ← 実装・実行
  ↓
Measure       ← 結果の計測
  ↓
Generalize    ← 学びの抽象化・再利用
```

**v0.1 では、これを以下の最小ループに圧縮する。**

```
Goal → Plan → Build → Review → Improve
```

各ステップの詳細は [`workflow/v0.1.md`](workflow/v0.1.md) を参照。

## 評価基準

このフレームワークが「機能している」かどうかは、以下 3 点で評価する。

| 基準 | 問い |
|---|---|
| Domain independence | このフレームワークを別ドメインで使うとき、`framework/` の変更が最小で済むか？ |
| Agent replaceability | 使う AI モデルを差し替えても、同じ手順で問題解決ループを回せるか？ |
| Reproducibility | 過去の run を参照すれば、なぜその結論に至ったかを再現・追跡できるか？ |

## templates/ と runs/_template/ の役割差

このフレームワークには「テンプレート」が 2 か所ある。混同しないこと。

| パス | 役割 | 性質 |
|---|---|---|
| `framework/templates/` | **設計資産としての原本** | 各ステップの汎用ひな型。ドメイン・ケースを問わず共通。編集・改訂は慎重に。 |
| `runs/_template/` | **run 開始時にコピーする運用ひな型** | 実行単位の記録ファイル群。新しい run を切るたびにコピーして使う。 |

`framework/templates/` は仕様書。`runs/_template/` はその仕様書から作った用紙。
用紙（run）に書いた内容を反省して、仕様書（templates）を改訂する循環が望ましい。

## 一次記録と二次成果物

run のファイルには 2 種類の性質がある。

### 一次記録（正式記録）

goal.md 〜 result.md は**一次記録**である。
各ステップで実際に書かれた事実・判断・引き継ぎ内容が含まれる。
厳密な事実確認・再現・比較にはこちらを参照する。

```
execution-assignment.md  how to run
goal.md                  what to solve
plan.md                  how to approach
handoff.md               conditional transfer context between roles
build.md                 what was made
review.md                what was found
improve.md               what was decided
result.md                what was learned
```

### 二次成果物（可読化ファイル）

**transcript.md** は**二次成果物**である。
一次記録を置き換えるものではなく、
run 完了後に「役割別の発言形式で再構成した可読化文書」として生成するファイルである。
逐語ログでも、会話の再現でもない。

transcript.md の目的:
- 読みやすさ: 複数ファイルを順番に開かなくても run の流れが分かる
- 共有性: 他人に「この run で何があったか」を伝えやすい
- 振り返り性: 時間が経ってから run を振り返るときの入口として使える

transcript.md の制約:
- **一次記録の正確性を保持する**（創作・補足・解釈を加えない）
- **元ファイルにない発言・判断を「それっぽく」補完・創作しない**（逐語ログでも会話の再現でもない）
- **handoff の記述は要約で書く**（引用ブロックより要約の方が事実性を担保しやすい）
- **result.md 完了後に生成する**（途中生成は事実関係が不完全になる）
- optional だが、初回 run・重要 run・資産化したい run では **strongly recommended**

詳細は [`workflow/v0.1.md`](workflow/v0.1.md) の Step 7 を参照。

## 設計上の制約

- **過剰な抽象化を避ける**: 実際に使える最小構成を優先する
- **ツール非依存**: 特定の IDE・CLI・SaaS に依存しない
- **人間が主体**: AI は問題解決の道具。判断の最終責任は人間が持つ
- **段階的拡張**: v0.1 → v0.2 → ... と incrementally 改善する

### P-01: 目的カテゴリ先行（Category-first structuring）

**考え方**
AI に自由生成させる前に、「何のための出力か」という目的カテゴリを人間が先に定義する。
生成 AI は探索空間が広いほど出力が散漫になりやすい。
カテゴリという枠を先に与えることで、網羅性と一貫性が同時に上がる。

**何に効くか**
- 生成物の抜け漏れ防止（カテゴリ単位で「出そろったか」を確認できる）
- JuniorBuilder / Builder への分業軸を与える
- Review 時に「このカテゴリは充足されているか」という評価軸になる

**どんなケースに向くか**
複数パターンを一括生成したいコンテンツ系 run 全般。
SNS テンプレート・教材コンテンツ・LP コピー・メール文面など、
出力の「種類」が複数ある場面で特に効く。

**有効な phase**: Plan（Planner がカテゴリを定義してから Generate に入る）

---

### P-02: テンプレートとインスタンスの分離（Template / Instance separation）

**考え方**
再利用可能な汎用骨格（テンプレート）と、個別の値（インスタンス）を混在させない。
`{{変数名}}` のようなプレースホルダーで可変部分を明示することで、
テンプレートを資産として管理しやすくなる。

**何に効くか**
- テンプレートの再利用性が上がる
- 「どこが毎回変わるのか」が明示され、運用者のミスが減る
- framework 自体の `runs/_template/`（汎用雛形）と `runs/`（実行コピー）の分離と同じ思想

**どんなケースに向くか**
成果物がドキュメント・コンテンツである run 全般。
プレスリリース・議事録・週次レポートなど、定期的に使い回す文書の作成に向く。

**補足**
変数形式はプロジェクト内で統一しておくと扱いやすい（例: `{{snake_case}}`）。
「あえて変数 0」で完全汎用設計にする判断も有効な選択肢。

**有効な phase**: Build（生成時に適用）。goal.md の成功基準に「変数が明示されているか」を含めると Goal 段階から一貫する。

---

### P-03: 2 段階生成（叩き台 → 仕上げ）

**考え方**
最初から完成品を狙わず、速度・網羅優先の叩き台フェーズ（JuniorBuilder）と
品質・統一性優先の仕上げフェーズ（Builder）を明示的に分ける。
1 回で全てを兼ねようとする single-pass 生成より、安定した品質を出しやすい。

**何に効くか**
- 生成が「詰まる」リスクを下げる（叩き台は完成品でなくてよいため心理的ハードルが低い）
- Builder が 0 から作るより、精査・改善の方が速く品質も安定する
- JuniorBuilder の出力がそのまま使える場合は仕上げコストを節約できる（上振れ）

**どんなケースに向くか**
コンテンツ生成・アイデア出し・バリエーション展開が必要な run。
「最初から品質を求めると止まる」と予想できる場面で特に有効。

**補足**
JuniorBuilder は CLI ツールでなく human が代行してもよい。
重要なのはフェーズ分離の意識であり、executor の種類は問わない。

**有効な phase**: Build 全体（JuniorBuilder → Builder の順番で構成する）

---

### P-04: 3 段階評価（Critical / Major / Minor）

**考え方**
Critic のレビュー指摘を重みで分類し、採用判断の閾値を事前に決めておく。
「Minor のみなら即採用、Major 以上があれば修正後採用または却下」のような基準を持つことで、
完璧主義による停滞を防ぎ、意思決定を速くできる。

**何に効くか**
- Judge / 人間の採用判断コストが下がる
- 「全指摘を直してから進む」という詰まりを回避できる
- 「完璧より完走」という framework の v0.1 思想と整合する

**どんなケースに向くか**
- 初回 run・v0.1 段階など、完走を優先すべき場面
- 成果物が複数ある run で、優先順位をつけて段階的に改善したい場合

**補足**
Critical / Major / Minor の定義は run ごとに毎回書く必要はないが、
Critic プロンプトに含めると出力の一貫性が上がる。

**有効な phase**: Review（Critic の出力形式として指定）、Improve（Judge の採用判断基準として参照）

---

### P-05: Improve Plan を実行指示書として設計する（Improve Plan as executable instruction）

> 初出: `runs/2026-03-16_sochi-blocks_sns-post-template-v2`（v0.2 初回試験 run）
> 今後の run で追加検証予定。

**考え方**
Improve Plan は「改善方針のメモ」ではなく、「実行者が迷わず動ける命令書」として設計する。
転記元テーブル・具体例・判断の根拠を Improve Plan 内に埋め込むことで、
実行者（AI / CLI / Human）が外部ファイルを調べ直す必要をなくせる。
命令書が自己完結するほど、executor の種類を問わず委譲しやすくなる。

**何に効くか**
- Improve 実行時の判断コストを下げる（「何の値を使うか」の問い合わせがなくなる）
- 実行者が自分以外の場合でも品質ブレが起きにくくなる
- framework の思想「人間がこだわりを定義し、AI がそれを増幅する」の実装パターンになる

**どんなケースに向くか**
転記・構造追加など、実行者が元ファイルから値を探す必要がある改善。
実行者が AI / CLI / 別の人間であるなど、判断の委譲が必要な run 全般。

**補足**
「判断コストをゼロにする」のが目的であり、Improve Plan を詳細にすること自体が目的ではない。
文言生成など「生成が必要な改善」では、今回のような転記元埋め込みだけでは不十分になる可能性がある（今後の検証課題）。

**有効な phase**: Improve Plan（Judge が作成する際に具体データを埋める）

---

### P-06: Done Criteria を測定可能な形で書くと Verify が受け入れ判定として機能する（Done Criteria-based verification）

> 初出: `runs/2026-03-16_sochi-blocks_sns-post-template-v2`（v0.2 初回試験 run）
> 今後の run で追加検証予定。

**考え方**
Verify は「成果物の品質を再評価する場」ではなく、
「Improve Plan の Done Criteria を満たしているかを照合する場」として設計する。
Done Criteria を「存在確認・数値確認」など測定可能な形で書くことで、
Verify の問いが「何が問題か（発見）」から「条件を満たしているか（確認）」に変わる。

**何に効くか**
- Verify が Review の焼き直しになるリスクを構造的に防ぐ
- 受け入れ基準が Improve Plan に明文化されることで、Judge の判断コストが下がる
- Pass / Conditional / Fail の判定が速くなる

**どんなケースに向くか**
構造変更・転記・列追加など、「条件を満たしているか」が機械的に確認できる改善。
「全 N 行に列が存在するか」「文字数制限を守っているか」のように、
合否が明確な Done Criteria を書ける場面で特に有効。

**補足**
Done Criteria の書き方が曖昧（「品質が高いか」「適切か」など）だと、
Verify が結局 Review と同じ性質になる。
質的判断が避けられない改善では、Done Criteria の設計自体が難しくなる（今後の検証課題）。

**有効な phase**: Improve Plan（Done Criteria を書く時）、Verify（照合実行時）

---

### P-07: 非スコープの明示（Explicit non-scope declaration）

> 初出: `runs/2026-03-16_sochi-blocks_sns-post-template-v2`（v0.2 初回試験 run）
> 今後の run で追加検証予定。

**考え方**
Improve Plan に「今回対応しない修正（理由付き）」を明示的に書くことで、
実行者が「ついでに直す」という scope creep を構造的に防ぐ。
「やること」だけでなく「やらないこと」を定義することが、スコープ管理の鍵になる。

**何に効くか**
- 実行スコープの意図しない拡大を防ぐ
- 改善候補が複数ある run で、今回の対象と後回しの対象を明確に分けられる
- 「善意の過剰改善」（特に AI executor で起きやすい）を防げる

**どんなケースに向くか**
改善候補が複数ある run で、今回は一部だけに絞りたい場面。
P-05（Improve Plan を命令書として設計する）と組み合わせると特に効果的。

**有効な phase**: Improve Plan（「Fix Scope — 対応しない修正」セクション）

### P-08: 2 段階運用（Two-phase operation）

> 初出: `runs/2026-03-16_sochi-blocks_sns-post-template-v2` の Framework Feedback より抽出。
> 現時点では「次 run の実験候補」であり、framework の正式 default ではない。

**考え方**
run 全体を「設計・承認フェーズ」と「実行フェーズ」に分割する。

- **フェーズ 1（設計・承認）**: Goal → Plan → Improve Plan を先に作り、人間が確認する
- **フェーズ 2（実行）**: 承認済みの Improve Plan を起点に Improve → Verify → Result を走らせる

フェーズ 1 で人間がこだわりと判断基準を定義し、フェーズ 2 で AI / CLI がそれを実行する。
「人間がこだわりを定義し、AI がそれを増幅する」という framework の思想に合う分割。

**何に効くか**
- フェーズ 2 を AI / CLI executor に委譲しやすくなる
- Improve Plan が「承認済みの仕様書」として機能し、実行中の迷いがなくなる
- フェーズ間の責務境界が明確になる

**どんなケースに向くか**
実行者が AI / CLI であるか、実行フェーズを自律的に動かしたい run。
改善スコープと Done Criteria が承認前に確定できる場合に向く。

**留保事項**
- Build・Review も含めたフルフロー（Build → Review → Improve Plan → ...）での検証はまだ
- フェーズ 1 に Build / Review を含めるかはケースによって異なる可能性がある
- （更新）文言生成タスク（C2）でも Build → Review → Verify の分離が機能することを確認。承認粒度の懸念は解消

**有効な phase**: run 全体の設計時（execution-assignment.md または plan.md で明示する）

### P-09: 文言生成は「生成」と「採択」を分離する（Generate-then-select）

> 初出: `runs/2026-03-16_sochi-blocks_sns-post-template-v2`（C2: D-2 CTA 追加）
> 文言生成タスクでの v0.2 フロー検証から抽出。

**考え方**
文言・コピーを改善する場合、「最善案を一発で決める」より
「複数アーキタイプの候補を生成し、Review で採択する」2 ステップに分けた方が機能する。

Improve Plan でアーキタイプ（方向性・制約）を先に定義し、Build で候補を生成、Review で比較選定する。
Build は採択判断をしなくてよいため、生成に集中できる。
Review は構造条件（Verify 相当）と質的観点（トーン・差別化・汎用性）を分離して評価できる。

**何に効くか**
- 文言の良し悪しを「感覚」から「定義済み評価観点での比較」に乗せられる
- Build 担当が「これで正しいか」を気にせず生成に集中できる
- 採択根拠が Review に残るため、次回修正時の判断材料になる

**どんなケースに向くか**
CTA・キャッチコピー・テンプレート文言・見出しなど、質的判断が伴うコピー改善全般。
「正解が 1 つとは言えないが、明らかに比較できる軸がある」場面で特に有効。

**補足**
アーキタイプの定義は Improve Plan（Executor Notes）に書く。
「測定型 / 挑戦型 / 招待強化型」のように方向性と制約を明示すると、Build の生成精度が上がる。
アーキタイプが本当に異なる価値を提供しているかは Review が判断する。

**有効な phase**: Improve Plan（アーキタイプ定義）、Build（候補生成）、Review（採択判断）

---

### P-10: 定性的な品質条件を構造ルールに変換する（Qualitative-to-structural conversion）

> 初出: `runs/2026-03-16_sochi-blocks_sns-post-template-v2`（C2: D-2 CTA 追加）
> 文言生成タスクでの v0.2 フロー検証から抽出。

**考え方**
「行動誘発として機能するか」「トーンが合っているか」のような定性的な条件をそのまま
Done Criteria に書くと、Verify が Review の焼き直しになる。

定性条件を構造ルール（形式・文字数・禁止語）に変換することで、Verify の問いが
「良いか（判断）」から「条件を満たすか（確認）」に変わる。
変換できない質的判断は Review に委ね、Verify は構造条件に絞る役割分担が鍵。

**変換例（C2 での実例）**:
- 「行動誘発として機能するか」→「〜してください / てみてください / 解けますか？形式で終わる」
- 「知的トーンを維持しているか」→「感嘆符（！）なし」「30 文字以内」

**何に効くか**
- Verify と Review の役割が実務レベルで分離する
- Done Criteria の合否が速く判定できる
- 「定性的なので Verify できない」という思い込みを崩せる

**どんなケースに向くか**
コピー・文言・デザインのように「良し悪しが主観的」に見えるが、
特定の構造条件（長さ・形式・語彙制約）に落とせる改善全般。
P-06（Done Criteria を測定可能な形で書く）と組み合わせると効果が高い。

**補足**
構造ルールに変換できる部分と、できない部分（例: 「全体的なトーン整合」）がある。
変換できない部分は Review の質的評価に委ねる。これを「できない」とするのではなく
「Review と Verify で役割分担する」と捉えることが設計の核心。
