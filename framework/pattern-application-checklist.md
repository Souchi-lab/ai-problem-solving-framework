# Pattern Application Checklist

> **このファイルは何か**
> `framework/overview.md` の再利用可能パターン（P-01〜）を、
> 「知識として読む」ではなく「run 設計時に適用判断できる問い」に変換したチェックリスト。
>
> **いつ使うか**
> - 新しい run を始める前
> - plan.md を書く前（Planner として考えるとき）
> - Review・Improve のフェーズを設計するとき
> - result.md で学びを整理したあと、次 run に活かすとき
>
> **overview.md との違い**
> overview.md = パターンの概念整理（何で・なぜ有効か）
> このファイル = run 設計時の判断補助（今回使うべきか）

---

## 使い方

1. 新しい run を切る前に、このファイルをざっと見る
2. 「今回の run に当てはまる問い」だけチェックする（全部見なくてよい）
3. 適用すると判断したパターンは、plan.md または goal.md の設計に反映する
4. run 完了後、result.md の Generalization と照らして「どのパターンが機能したか」を振り返る

---

## 共通ルール

- **全パターンを毎回使う必要はない**。今回の run に合うものだけ使う。
- パターンは手段であり目的ではない。「パターンを適用すること」が目標にならないようにする。
- 迷ったら使わない。run を複雑にするより完走する方が学びになる。
- パターンが増えたら、このファイルにセクションを追加するだけでよい。

---

## P-01: 目的カテゴリ先行

**一言**: 生成前にカテゴリを人間が定義すると、AI の出力が網羅的かつ一貫する。

**これを使うと何が減るか**: 生成物の抜け漏れ・後からカテゴリを足す再作業・「何を作ればよいか」という迷い

### 自問チェック項目

- [ ] 今回の成果物は、複数の「目的」や「用途」に分けられるか？
- [ ] AI に「自由に作ってください」と渡した場合、カテゴリの偏りや抜けが起きやすいか？
- [ ] カテゴリごとに「どうなったら十分か」を先に定義した方が、Review が速くなるか？
- [ ] 成果物の種類が 3 つ以上になりそうか？（3 つ以上になるなら先に分類する価値がある）

### どんな run で有効か

複数パターンを一括生成するコンテンツ系 run。
SNS テンプレート・教材コンテンツ・LP コピー・メール文面など、
「出力の種類が複数ある」場面で特に効く。

### 使わない方がよいケース

- 成果物が 1 種類で完結する run（例: 単一のドキュメント改訂）
- カテゴリ設計自体がタスクの本質になっている場合（先行定義が難しい）
- 探索型の run でまずアイデアを出させたい場面（カテゴリが決まる前に生成させた方がいい場合もある）

### よくある失敗

- カテゴリを「なんとなく」で雑に作ると、Build の後に「このカテゴリは要らなかった」「もう 1 種類足りない」が発生する
- カテゴリ設計に凝りすぎて、Plan が過剰になり Build が遅れる

### 適用する場合の反映先

| フェーズ | 反映内容 |
|---|---|
| `goal.md` | 成功基準に「各カテゴリが充足されているか」を追加 |
| `plan.md` | Problem Structure にカテゴリ一覧を定義する |
| `build.md` | カテゴリごとに成果物を整理する構成にする |
| `review.md` | 「このカテゴリは充足されているか」という評価軸で Critic に渡す |

## P-02: テンプレート / インスタンス分離

**一言**: 汎用骨格（テンプレート）と個別値（インスタンス）を混在させないと、再利用性が上がる。

**これを使うと何が減るか**: 同じ構造の再作成・コピーミス・「どこが変えてよい部分か」という迷い

### 自問チェック項目

- [ ] 今回作る成果物は、「毎回変わる部分」と「毎回変わらない部分」に分けられるか？
- [ ] 同じ構造を持つ成果物を複数作るか、または今後繰り返し使う可能性があるか？
- [ ] `{{変数}}` のようなプレースホルダーを使うと、運用者が迷わず入力できるようになるか？
- [ ] 今回の成果物に run 固有の情報（特定の日付・固有名詞）を「構造」に埋め込みすぎていないか？

### どんな run で有効か

成果物がドキュメント・コンテンツである run 全般。
定期的に繰り返す文書（SNS 投稿・議事録・週次レポート・メール文面）に特に向く。

### 使わない方がよいケース

- 1 回限りの成果物で再利用の予定がない場合（変数化のコストが無駄になる）
- 変数の数が多くなりすぎて、テンプレートが使いにくくなる場合（変数が 6 つ以上になったら見直す）
- 成果物の「構造」自体がまだ確定していない探索フェーズ（先に構造を決めてから変数化する）

### よくある失敗

- 変数に入れるべき部分を固定テキストにしてしまい、「あのテンプレートは〇〇向けにしか使えない」になる
- 逆に変数を増やしすぎて、実際に使うときに埋めるのが大変になる

### 適用する場合の反映先

| フェーズ | 反映内容 |
|---|---|
| `goal.md` | 成功基準に「変数が明示されているか」を追加 |
| `build.md` | `{{変数名}}` 形式を使い、変数の説明セクションを添える |
| `review.md` | 「変数の意味・形式が明確か」を評価観点に追加 |

## P-03: 2 段階生成（叩き台 → 仕上げ）

**一言**: 最初から完成品を狙わず、「速く広く出す」フェーズと「整えて完成させる」フェーズを分ける。

**これを使うと何が減るか**: 生成の詰まり・最初の 1 案への固執・「全部ゼロから作る」コスト

### 自問チェック項目

- [ ] 最初から完成品を求めると、生成が止まったり品質が不安定になりそうか？
- [ ] まず「広く候補を出す」フェーズと「絞り込んで仕上げる」フェーズを分けると効率がよいか？
- [ ] Builder が 0 から作るより、叩き台をベースに精査・改善する方が速そうか？
- [ ] 今回のタスクは「網羅性（多く出す）」と「品質（整える）」が同時に要求されているか？

### どんな run で有効か

コンテンツ生成・アイデア出し・バリエーション展開が必要な run。
「いきなり完成品を作ろうとすると詰まる」と予想できる場面で特に有効。
成果物が 5 本以上になる場合は特に 2 段階に分ける価値がある。

### 使わない方がよいケース

- 成果物が 1〜2 件と少なく、1 ステップで完成できる場合（2 段階のオーバーヘッドが無駄）
- 叩き台の品質が低すぎると Builder のコストが増える（叩き台に最低限の制約を与えること）
- 時間・コストが限られていて 1 ステップしか使えない場合

### よくある失敗

- JuniorBuilder に制約なく自由生成させると、使えない叩き台ばかりになり Builder が 0 から作り直す羽目になる
- 「叩き台だから雑でいい」が行き過ぎて、Builder が叩き台を見ないで再生成する（= 1 段階のコスト × 2）

### 適用する場合の反映先

| フェーズ | 反映内容 |
|---|---|
| `execution-assignment.md` | JuniorBuilder の executor と生成ルールを事前定義する |
| `plan.md` | Build セクションに「JuniorBuilder → Builder」の 2 段階構成を明記する |
| `build.md` | JuniorBuilder の出力を workspaces/ に保存し、Builder の判断を記録する |

## P-04: 3 段階評価（Critical / Major / Minor）

**一言**: 指摘の重みを分類し、採用判断の閾値を先に決めることで、完璧主義の詰まりを防ぐ。

**これを使うと何が減るか**: 「全部直してから進む」による停滞・採用判断の迷い・Minor に引きずられる判断ロス

### 自問チェック項目

- [ ] 今回のレビューは「指摘の列挙」で終わる可能性があるか？（判断なく指摘だけ並ぶのを防ぎたい）
- [ ] Critical / Major / Minor を分けることで、「Minor だけなら採用」という判断基準を先に置けるか？
- [ ] 完走を優先すべき run か？（初回 run・探索フェーズ・時間制約がある場合）
- [ ] Critic に渡す前に、どの指摘が「致命的」でどれが「あったらよい改善」かを定義できるか？

### どんな run で有効か

- 初回 run・v0.1 段階など「まず完走する」を優先すべき場面
- 成果物が複数あり、優先順位をつけて段階的に改善したい場合
- Critic が「なんでも指摘する」傾向がある場合（指摘の粒度をそろえる効果もある）

### 使わない方がよいケース

- 品質基準が絶対的に高く、Minor でも全て対応が必要な場合（医療・法務・財務系の重要文書など）
- 成果物が 1 件でシンプルな場合（3 段階の分類自体が過剰になる）

### よくある失敗

- Critical / Major / Minor の定義をしないまま使うと、「これは Major か？」でもめる
- Judge が Minor を無視しすぎて、次 run にも積み残しが続く（次 run のスコープに入れておく）
- Critic が全指摘を Minor にして「安全に逃げる」パターン（Critical/Major の判断を明示的に求める）

### 適用する場合の反映先

| フェーズ | 反映内容 |
|---|---|
| `goal.md` | 「Minor のみなら採用」という採用基準を Success Criteria に入れる |
| `plan.md` | Critic への指示に「Critical / Major / Minor で分類」を明記する |
| `review.md` | 指摘を 3 段階で分類し、Critical / Major が 0 件かどうかを総評に入れる |
| `improve.md` | 採用・却下の根拠に「Critical/Major/Minor の件数」を使う |

## v0.2 パターン群（簡易版）

> P-05 以降は v0.2 フロー（Improve Plan / Improve / Verify）に関連するパターン。
> 詳細は `framework/overview.md` を参照。ここでは「使うべきか」の判断問いのみ記載する。

### P-05 / Improve Plan を実行指示書として設計する

- [ ] Improve を自分以外の executor（AI / 別の人）に渡すか？
- [ ] 実行者が外部ファイルを調べ直さなくて済むよう、Improve Plan に具体データを埋め込めるか？

### P-06 / Done Criteria を測定可能な形で書く

- [ ] Verify が「新たな問題を探す場」になるのを防ぎたいか？
- [ ] 完了条件を「存在確認 / 数値確認」など合否が明確な形で書けるか？

### P-07 / 非スコープの明示

- [ ] 改善候補が複数あり、今回は一部だけに絞りたいか？
- [ ] AI executor に渡す場合、「ついでの改善」を防ぎたいか？

### P-08 / 2 段階運用（設計・承認 → 実行）

- [ ] フェーズ 1（Goal → Plan → Improve Plan）を人間が承認してから、フェーズ 2（Improve → Verify）を AI / CLI に委譲したいか？

### P-09 / 文言生成の「生成」と「採択」を分離する

- [ ] コピー・文言・見出しのような質的判断が伴う改善か？
- [ ] Build に「最善案を決める」責務を持たせず、候補生成に集中させたいか？

### P-10 / 定性的な品質条件を構造ルールに変換する

- [ ] Done Criteria が「良いか」「適切か」という質的判断になってしまっているか？
- [ ] 形式・文字数・禁止語など構造条件に落とせる部分があるか？

## 使い方例

> 以下は判断フローの例。事例依存にせず、「どんな run でも使える問い方」にしている。

**コンテンツ生成系 run を始める前**:
```
□ 出力の種類が複数か？ → P-01（カテゴリ先行）を検討
□ 成果物を繰り返し使うか？ → P-02（テンプレート分離）を検討
□ 生成量が多くて詰まりそうか？ → P-03（2 段階生成）を検討
```

**Review フェーズを設計するとき**:
```
□ 採用判断を速くしたいか？ → P-04（3 段階評価）を検討
□ Verify が再レビューになるのを防ぎたいか？ → P-06（Done Criteria 測定可能化）を検討
```

**Improve Plan を書くとき**:
```
□ 別 executor に渡すか？ → P-05（実行指示書設計）を検討
□ 改善候補が複数あるか？ → P-07（非スコープ明示）を検討
□ 文言・コピー改善か？ → P-09（生成と採択の分離）を検討
```

---

*このチェックリストは rigid な手順書ではなく、run 設計時の思考補助ツールである。*
*パターンを全部適用することが目的ではない。今回の問題に合うものだけ選んで使う。*
