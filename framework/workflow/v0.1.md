# Workflow v0.1

## 概要

v0.1 の workflow は以下の 6 ステップで構成される。

```
Goal → Plan → Build → Review → Improve → Result
```

**Result を明示ファイルとして持つことが v0.1 の要件。**
result.md を書くまで run は「完了」ではない。

役割の受け渡し（handoff）は `handoff.md` を通じて行う。
モデルを分けるほど、この文書の質が problem solving の品質に直結する。

Result 完了後に、任意の補助ステップとして **Transcript** を追加できる。

```
Goal → Plan → Build → Review → Improve → Result
                                              ↓ (optional)
                                          [Transcript]
```

Transcript は正式な実行ステップではない。
run の記録を「会話形式で読み直せる二次成果物」として生成する補助作業である。
詳細は下記 Step 7 を参照。

---

## 各ステップの定義

### 1. Goal

**目的**: 解く問題と成功条件を明確にする

| 項目 | 内容 |
|---|---|
| 入力 | 問題の気づき・背景情報・制約条件 |
| 出力 | 明確化された Goal / 背景 / 制約 / 成功基準 |
| 担当 role | 人間（必須） |
| handoff 先 | → Planner |

**ルール**:
- Goal が曖昧なまま Plan に進まない
- 「何を達成したら成功か」を必ず定義する
- model-assignment.md もここで作成する

---

### 2. Plan

**目的**: 問題を分解し、解決アプローチを選択する

| 項目 | 内容 |
|---|---|
| 入力 | `goal.md` + `model-assignment.md` |
| 出力 | `plan.md`（問題構造 / 仮説 / 選択肢 / 採用アプローチ / 実行計画） |
| 担当 role | **Planner**（人間 + AI 推奨） |
| handoff 先 | → JuniorBuilder または Builder |

**ルール**:
- 最低 2 つ以上のアプローチを比較・検討する
- 採用しなかった選択肢と理由も記録する
- `handoff.md` を作成して次の role に引き渡す

---

### 3. Build

**目的**: Plan に基づいて実装・成果物を作る

| 項目 | 内容 |
|---|---|
| 入力 | `plan.md` + `handoff.md`（Planner または JuniorBuilder から） |
| 出力 | 成果物 + `build.md` |
| 担当 role | **Builder**（高品質モデル推奨） |
| handoff 先 | → Critic |

**ルール**:
- **高品質モデルをこの工程に集中投入する**（コストをかけるべき工程）
- JuniorBuilder が候補を用意している場合は、それを判断・統合する
- Plan から逸脱した場合は `build.md` に理由を記録する
- `handoff.md` を更新して Critic に引き渡す

---

### 4. Review

**目的**: 成果物の問題点・リスク・改善点を洗い出す

| 項目 | 内容 |
|---|---|
| 入力 | `build.md` + 成果物 + `handoff.md`（Builder から） |
| 出力 | `review.md`（Critical / Major / Minor に分類した指摘） |
| 担当 role | **Critic**（Builder と別モデル推奨） |
| handoff 先 | → Judge / Improve |

**ルール**:
- **Critic は Builder と異なるモデル・視点で評価する**（同一モデルは避ける）
- 「褒める」のではなく「壊す」視点で臨む
- Critical / Major / Minor で重要度を分類する

---

### 5. Improve

**目的**: 次のイテレーションのスコープを定義する、またはループを完了する

| 項目 | 内容 |
|---|---|
| 入力 | `review.md` |
| 出力 | `improve.md`（次 iteration のスコープ or 完了判定） |
| 担当 role | **人間（Judge）** |
| handoff 先 | → Plan/Build（次 iteration）または → Result |

**ルール**:
- Review の全指摘を次 iteration で解決しようとしない
- 「完了」と判断したら Result ステップへ進む

---

### 6. Result

**目的**: このループの最終記録を残す

| 項目 | 内容 |
|---|---|
| 入力 | `improve.md` + 全ファイル |
| 出力 | `result.md`（Outcome / 成否 / Lessons / Generalization / Reusable assets） |
| 担当 role | 人間（必須） |

**ルール**:
- `result.md` を書くまでその run は「完了」ではない
- **Generalization と Reusable Prompt は必ず書く**（これがフレームワークの核心）
- 他ドメインに横展開できる知見を抽象化する

---

---

### 7. Transcript（補助ステップ — optional but recommended）

**目的**: run の正式記録（goal.md 〜 result.md）を会話形式で再構成し、読みやすさ・共有性・振り返り性を高める

| 項目 | 内容 |
|---|---|
| 入力 | `execution-assignment.md` / `goal.md` / `plan.md` / `handoff.md` / `build.md` / `review.md` / `improve.md` / `result.md` |
| 出力 | `transcript.md`（会話形式の run サマリー） |
| 担当 | 人間（または AI を使って生成） |
| タイミング | `result.md` 完了後 |

**これは正式記録ではない**:
- goal.md 〜 result.md = **一次記録**（事実・判断の正式な根拠）
- transcript.md = **二次成果物**（一次記録を読みやすく再構成したもの）

一次記録は transcript.md によって置き換えられない。
厳密な事実確認は常に元ファイルを参照すること。

**なぜ最後に生成するか**:
- 全ステップが完了してからでないと全体の流れを正確に追えない
- 途中生成すると事実関係が不完全になる

**特に有用なケース**:
- 初回 run（フレームワーク自体の動作確認として記録価値が高い）
- 重要な意思決定を含む run（Judge の判断根拠を後から追跡したい）
- 他人に共有したい run（複数ファイルを読まずに全体を把握してもらえる）
- 資産化したい run（Generalization の背景ストーリーを残したい）

**生成方法（手動）**:

```
1. transcript.md のひな型を開く（runs/_template/transcript.md）
2. 各セクションに対応するファイルを参照する
3. 「誰が何を言い、何を決め、何を次へ渡したか」を会話形式で記述する
4. 創作しない。元ファイルに書かれていないことを追加しない
```

**生成方法（CLI 補助）**:

```bash
apsf generate-transcript <run-name>
# 参照すべきファイルの一覧と各セクションの記入ガイドを表示する
```

## handoff のタイミング

```
[人間] Goal → handoff → [Planner] Plan
[Planner]   Plan → handoff → [JuniorBuilder] 候補出し（任意）
[JuniorBuilder] → handoff → [Builder] 実装
[Builder]   Build → handoff → [Critic] Review
[Critic]    Review → (handoff) → [人間/Judge] Improve/Result
```

handoff.md には「現状 / 決定済み / 未決 / 次にやること / 制約」を必ず含める。

---

## 最小運用ルール

- 1 run = 1 問題 = `runs/YYYY-MM-DD_case-key_topic/` の 1 フォルダ
- run 開始時に `execution-assignment.md` と `model-assignment.md` を最初に作る
- `result.md` を書くまで run は「完了」ではない
- 途中で中断する場合も `result.md` に理由を記録する
- `transcript.md` は optional だが、初回 run・重要 run では強く推奨する

## CLI サポートコマンド

v0.1 には Human-in-the-loop を支援する CLI コマンドが含まれる。

```bash
apsf start-run <case-key>_<topic>    # run ディレクトリを作成（日付自動付与）
apsf start-run <name> --dry-run      # 作成内容をプレビュー（実際には作成しない）
apsf next <run-name>                 # 現フェーズを検出して次ロール向け指示を表示
apsf next <run-name> --debug         # フェーズ判定根拠も表示
apsf transcript <run-name>           # transcript.md を自動生成
```

**`apsf next` は提案型**である。ファイルの存在・充填状態から推定するため、
結果はあくまで参考。最終判断は Human が行う。

詳細: `framework/cli-orchestrator.md`

## v0.2 以降の拡張方向性

| 項目 | v0.1 | v0.2+ |
|---|---|---|
| Judge | 人間が兼任 | 独立 Agent として定義 |
| Pipeline | 手動 | CLI / Python で自動実行 |
| JuniorBuilder | 任意 | 標準ステップ化 |
| 並列実行 | 未対応 | 複数 Plan の並列 Build・比較 |
| handoff | 手動作成 | 自動生成 |
