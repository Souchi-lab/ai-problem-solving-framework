# Workflow v0.2

## 変更の動機

v0.1 の Improve フェーズは、以下の 3 つの異なる仕事を 1 ステップに混在させていた。

1. 何をどう直すかを決める（改善計画）
2. 実際に直す（改善実行）
3. 直した結果が妥当かを確認する（改善判定）

これらは異なる能力・異なる責務であり、実行者が AI / CLI / Human のいずれであっても、
「何を直すか / どこまで直すか / 何は直さないか / どうなったら合格か」を
事前に明文化した方が、判断を安全に委譲できる。

また、修正後には「本当に要求を満たしたか」を確認する独立したフェーズが必要になる。

v0.2 では、この問題を **Improve Plan / Improve / Verify** の 3 段階分解で解決する。

---

## v0.2 ワークフロー

```
Goal → Plan → Build → Review → Improve Plan → Improve → Verify → Result
                                                                   ↓ (optional)
                                                               [Transcript]
```

### v0.1 との差分

| フェーズ | v0.1 | v0.2 |
|---|---|---|
| Improve | 方針決定・実行・判定を混在 | 実行のみ（範囲を絞る） |
| Improve Plan | なし（Improve に内包） | **新設**: 方針・スコープ・完了条件を定義 |
| Verify | なし（Improve に内包） | **新設**: 修正結果の受け入れ判定 |

**注**: Improve Plan と Verify は run の性質に応じて省略可能（省略基準は後述）。
v0.1 互換の最小ループ（`Improve Plan なし・Verify なし`）は引き続き有効。

---

## 各フェーズの定義

### 1〜4. Goal / Plan / Build / Review

v0.1 から変更なし。詳細は [workflow/v0.1.md](v0.1.md) を参照。

---

### 5. Improve Plan

**目的**: 改善の方針・修正スコープ・完了条件を、実行者に渡す前に明文化する

| 項目 | 内容 |
|---|---|
| 入力 | `review.md` + `goal.md` |
| 出力 | `improve-plan.md` |
| 担当 role | **Judge / 人間**（実行者への命令書として機能するため、人間が定義する） |
| handoff 先 | → Improve（実行者） |

**Improve Plan が定義すべき内容**:

- 対応する修正と優先度
- 対応しない修正（理由付き）
- 修正してよいファイル・修正してはいけない範囲
- 完了条件（どうなったら合格か）
- 実行者への注意事項

**なぜ必要か**:
「修正してください」と渡すだけでは、実行者（AI / CLI / Human）が迷う。
方針書があることで判断を安全に委譲できる。
また「何を直さないか」の明示は、完璧主義による過剰修正を防ぐ効果がある。

**省略できるケース**:
- 同一人物が Review → Improve まで連続して担当し、方針を自己完結できる場合
- Minor 指摘のみで、修正内容が明白な場合（単純な文言修正・誤字など）

---

### 6. Improve

**目的**: Improve Plan に従って成果物を修正する

| 項目 | 内容 |
|---|---|
| 入力 | `improve-plan.md` + `build.md` + 成果物 |
| 出力 | 修正後の成果物 + `improve.md`（実行記録） |
| 担当 role | **Builder / Human / CLI**（Improve Plan が渡されていれば executor を問わない） |
| handoff 先 | → Verify |

**ルール**:
- Improve Plan の範囲を超えた修正を自己判断で行わない
- Plan から逸脱した場合は `improve.md` に理由を記録する
- 「完了条件を満たしたか」の最終判断は Verify に委ねる（自己採点しない）

---

### 7. Verify

**目的**: 修正結果が Improve Plan の完了条件を満たしているかを判定する

| 項目 | 内容 |
|---|---|
| 入力 | `improve-plan.md` + 修正後の成果物 + `improve.md` |
| 出力 | `verify.md`（Pass / Conditional / Fail + 理由） |
| 担当 role | **Judge / 人間**（実行者とは別の役割が望ましい） |
| handoff 先 | Pass → Result、Conditional → Result（残件は次 run）、Fail → Improve 再実行 |

**Review との違い**:

| | Review | Verify |
|---|---|---|
| 対象 | Build の初回成果物 | Improve 後の修正済み成果物 |
| 問い | 「何が問題か？」 | 「修正は完了条件を満たしているか？」 |
| 担当 | Critic（adversarial） | Judge（acceptance check） |
| 評価基準 | goal.md から導出 | improve-plan.md の完了条件 |
| 出力 | `review.md` | `verify.md` |

**省略できるケース**:
- Improve Plan を立てていない（v0.1 互換の簡易ループ）
- Minor のみの修正で、即採用を既に決定している場合

---

### 8. Result

v0.1 から変更なし。詳細は [workflow/v0.1.md](v0.1.md) を参照。

## Improve 系 3 フェーズの省略基準

| 状況 | Improve Plan | Improve | Verify |
|---|---|---|---|
| 実行者が自分以外（AI / 別 executor） | **必須** | 必須 | **必須** |
| 修正範囲が広い（複数成果物・複数ファイル） | **必須** | 必須 | 推奨 |
| 品質基準が明確 / 監査・説明責任が必要 | 推奨 | 必須 | **必須** |
| Minor のみ・同一人物が通しで担当 | 省略可 | 必須 | 省略可 |
| v0.1 互換の簡易ループ | 省略可 | 必須 | 省略可 |

**v0.2 のデフォルト**: Improve Plan = **推奨**、Verify = **推奨**。

最小構成（= v0.1 互換）は `Improve Plan なし → Improve のみ → Verify なし`。
その場合も `improve.md` に判断根拠を記録する慣習は維持すること。

### Improve Plan の内容粒度について

Improve Plan には「何を直すか」の定義に加えて、
以下を含めることで Improve 実行時の判断コストを大きく下げられることが確認された。

- **修正しない範囲**: 実行者が「ついでに直す」scope creep を防ぐ
- **完了条件（Done Criteria）**: 存在確認・数値確認など測定可能な形で書くと、Verify が照合作業として完結する
- **転記元や具体データ**: 実行者が外部ファイルを調べ直す必要がなくなり、判断の余地が最小化される

特に「転記元テーブルを Improve Plan に埋め込む」パターンは、
構造変更・転記系の改善で効果的だった。

文言生成が必要な改善（C2）では、異なる方法で Improve Plan を自己完結させられることを確認した:
- **アーキタイプ定義**: 「測定型 / 挑戦型 / 招待強化型」のように方向性と制約を定義すると、Build が採択判断なしに生成に集中できる
- **Done Criteria の構造ルール化**: 「〜形式で終わる / 感嘆符禁止 / N 文字以内」のように構造条件に落とすことで、Verify が照合作業として完結する

---

### Verify の機能設計について

Verify を「新しい問題を探す場」ではなく「Done Criteria への照合」として絞ることで、
Review との役割が実務レベルでも明確に分離できることを確認した。

**Verify で「やらないこと」を明示する効果**:
- 完了条件に含まれない観点での評価をしない
- Improve Plan 外の改善提案をしない
- 新規問題の発見は次 run の Review に委ねる

この 3 点を Verify フェーズの責務から除外することで、
Verify の出力が Pass / Conditional / Fail + 照合テーブルとして完結した。

- 構造変更・転記中心の改善（C3: 早見表への列追加）

### 文言生成タスクへの v0.2 適用（C2 での確認）

> C2（D-2 CTA 追加）での実運用から得た補足知見。

---

**Build の責務を「生成のみ」に絞る**

文言・コピー改善では、Build に「最善案を選ぶ」責務を持たせない。
Improve Plan でアーキタイプ（方向性）を定義し、Build は候補を生成するだけにする。
採択判断は Review に委ねることで、Build / Review の責務が明確に分離できる。

```
Improve Plan → アーキタイプ定義（方向性・制約を明示）
Build       → 各アーキタイプの候補を生成（採択判断なし）
Review      → 構造条件を確認し、質的観点で比較採択
Verify      → 採択案が Done Criteria（構造ルール）を満たすか照合
```

---

**比較選定型 Review の設計**

文言生成タスクの Review は「問題を探す」レビューではなく「候補を比較して採択する」レビューとして設計する。

評価観点を事前に定義しておくことで、主観的な「なんとなく良い」を避けられる。評価観点の例:
- 行動の明確さ
- テンプレート全体のトーンとの整合
- 他テンプレートとの差別化
- 汎用性（全変数パターンに適用できるか）

質的判断は Review が担い、Verify は構造条件（形式・文字数・禁止語）の照合に絞る。

---

### 2 段階運用案（次 run の実験候補）

今回の run を振り返ると、自然と 2 段階に分かれていた。

- **フェーズ 1（設計・承認）**: Goal → Plan → Improve Plan を作り、人間が確認する
- **フェーズ 2（実行）**: 承認済みの Improve Plan を起点に Improve → Verify → Result を走らせる

この分割により、フェーズ 2 を AI / CLI executor に委譲しやすくなる。
現時点では framework の正式 default ではなく、**次 run の実験候補**として扱う。

検討が残る問い:
- Build・Review もフェーズ 1 に含めるべきか（含めるとフェーズ 1 が重くなる）
- 「承認」のタイミングは Improve Plan 確定後か Build 完了後か

有望と判断できれば `runs/_template/README.md` の運用フローへの反映を検討する。

## v0.3 以降の拡張方向性

| 項目 | v0.2 | v0.3+ |
|---|---|---|
| Improve Plan | 人間が手動作成 | Critic 出力を自動変換して生成 |
